# main、Release、安装包怎么选

**Release 是固定版本快照，不是“可直接安装”的保证；main 是持续更新的开发分支。** 判断能否安装，应看附件格式、匹配固件与验收记录。

## 当前版本关系

以下功能状态核对于 2026-10-22：

| 入口 | 包含什么 | 适合谁 |
| --- | --- | --- |
| [v0.1.1 Release](https://github.com/JasonBeam/openwrt-f50-plugins/releases/tag/v0.1.1) | 自适应 RA，以及对应快照中的独立小鲸插件；均为源码 | 想使用固定版本、核对变更并在 SDK 中构建的人 |
| [main](https://github.com/JasonBeam/openwrt-f50-plugins/tree/main) | 上述独立插件、后续文档，以及新增的 MU300 集成版刷新间隔补丁 | 需要未发布新功能或参与开发的人 |
| IPK / OpenWrt APK 附件 | 当前没有经过构建与全新安装验收的下载包 | 需要等待注明兼容范围的后续构建产物 |

新增间隔功能对应提交 [`c38d00a`](https://github.com/JasonBeam/openwrt-f50-plugins/commit/c38d00ab0ea3689e071dab702825f16c7ab92c49)。v0.1.1 的附件生成于此提交之前，所以下载旧附件不会得到新功能。

RA 与独立小鲸的包目录在这次间隔更新中没有变化；新内容针对已有 `f50.iot` 集成部署。不要为了给旧集成页面增加间隔控件，转而混装独立小鲸后台。

## 按需求选择

- **复现 v0.1.1 的独立插件行为**：取 v0.1.1 Release 源码，按相同版本说明准备 SDK。按功能拆分的 ZIP 仍是源码。
- **修改已有 MU300 流量池的刷新间隔**：取 main 完整源码，阅读 `integrations/mu300/README.md`；兼容性确认后，只在离线目录副本上生成补丁。
- **只想点一下就安装**：目前没有已验收的附件，不能把源码 ZIP 交给 opkg / apk，也不建议让 AI 随意复制文件到设备替代完整安装。

需要固定开发快照时，可以在开发电脑上使用 Git。新克隆的目录可以这样选择已发布版本：

```sh
git clone https://github.com/JasonBeam/openwrt-f50-plugins.git
cd openwrt-f50-plugins
git switch --detach v0.1.1
```

研究最新集成补丁时留在 main，并记录 `git rev-parse HEAD` 的输出。已有未提交修改时，先处理自己的工作，不要为了跟随教程执行强制重置。

## 要不要再发一个 Release？

**建议把新增集成补丁整理成下一次预发布 Release，便于用户固定下载和反馈；单纯调整首页排版则不必单独发版。** 新 Release 应明确区分独立包源码与已有部署补丁，不能因为有新标签就宣传成通用安装版。

这次文案更新不创建新标签、不替换 v0.1.1 附件。发布时应按实际变更确定版本号、更新 CHANGELOG 和 `docs/releases/`，再让自动工作流从标签提交打包。

当前打包器有一个必须注意的范围：

- 完整源码 ZIP 会包含标签提交中的全部已跟踪文件。
- 按功能拆分的 RA / 小鲸 ZIP 只选取独立包目录及公共文档，**不会包含 `integrations/` 和间隔补丁工具**。

因此，要把集成补丁做成独立下载入口，需要在后续发布中另外定义附件范围；在此之前，应指向包含新功能的完整源码，而不是小鲸独立包 ZIP。

## 安装包是否放 Release？

建议放。完成匹配 SDK 的构建和测试设备验收后，把 `.ipk` / OpenWrt `.apk` 当作明确的下载附件，注明固件、架构、依赖、包版本及校验值；不要把生成的安装包直接塞进源码目录。

哪些功能值得打包、格式如何选择，见[打包建议](PACKAGING.md)。发布步骤与源码检查见[贡献指南](../CONTRIBUTING.md)。
